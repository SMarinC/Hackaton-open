# Primer incremento de operación por video

Cada observación requiere `request_id` estable para reintentos y `expected_version` igual a la versión actual del caso para una solicitud nueva. Repetir el mismo ID con el mismo contenido devuelve `duplicate: true` sin nuevos efectos, incluso si el caso ya avanzó. Reutilizarlo con contenido distinto o registrar una nueva solicitud contra una versión anterior devuelve 409. Una observación posterior puede repetir el texto anterior si usa un ID nuevo y la versión vigente.

Los casos nuevos conservan `source` como evidencia inmutable de su evento inicial y lo identifican mediante `source_integrity: "opening_event_v1"`. Cada evento posterior guarda su propio payload validado en `events.payload`, sin reescribir fuente, versión ni cierre del caso. La migración agrega esa columna sin borrar datos; eventos anteriores quedan con `payload = NULL` y casos anteriores no reciben el marcador. La interfaz advierte que esas duraciones históricas pudieron mezclarse con eventos posteriores: no se reconstruye evidencia que ya no está disponible.

Cada evento puede conservar `detector` (texto), `threshold_s` (número positivo hasta 86400) y `zone_polygon` (3 a 20 vértices `[x, y]`, coordenadas entre 0 y 1) en `case.source`. Son la configuración de evidencia declarada por el detector del navegador; no una verificación independiente. El servidor registra sus propias fechas de recepción, sin confiar en `observed_at` para ordenar operaciones.

`node server/index.js` escucha en `127.0.0.1:8787` y sirve `dist/` si está construido. Requiere Node >=22.13 por `node:sqlite`. La base se conserva en `data/private/panela.sqlite`; no se debe versionar.

API: `GET /api/state`, `POST /api/events`, `POST /api/cases/:id/observation` y `POST /api/outbox/:id/send` (cuerpo JSON vacío para envío). Casos y outbox se persisten antes de devolver éxito. `event_id` se deduplica dentro de `run_id`; reutilizarlo con otro contenido produce 409. Los eventos aceptan `visit_id` estable por visita (por ejemplo, `track-1:visit-1`): fotogramas de esa visita/persona/zona/ejecución comparten caso, pero una reentrada con otro `visit_id` abre otro caso. Omitirlo usa el valor `legacy`, compatible con el contrato anterior, que no distingue reentradas. Una nueva ejecución necesita otro `run_id`.

La permanencia solo inicia una solicitud de revisión. `inventory` es un fixture identificado. Las observaciones `stock_confirmed`, `no_stock`, `restocked`, `no_issue` requieren nota y son **operador local sin autenticación de producción**, no respuestas de Slack/correo. `stock_confirmed` y `no_stock` exigen además el booleano `shelf_issue_confirmed: true`, que queda guardado en la observación: confirmar únicamente inventario no habilita una reposición ni una consulta al proveedor. `restocked` exige tarea asignada; `no_issue` descarta y no se cuenta como reposición. Los cierres guardan confirmación humana local, sin inventar verificación visual.

Los adaptadores salientes Slack Web API y Resend usan credenciales solo en servidor. Se requiere `PANELA_LIVE_SEND=true`, destinatario configurado y coincidencia exacta con allowlist. Eventos y observaciones producen outbox; con `PANELA_AUTO_SEND=true` además el servidor despacha en segundo plano los mensajes recién encolados de ese caso (tras responder al navegador). Sin esa variable, el despacho es manual con el botón **Enviar ahora** de la UI o `POST /api/outbox/:id/send`. Los mensajes se etiquetan como demo. Aceptación del proveedor no significa entrega, lectura o ejecución.

Al ejecutar `node server/index.js` (o `npm run dev`), los cambios en `.env` de credenciales, destinatarios y banderas de envío se aplican en caliente, sin reiniciar; `PORT` y `PANELA_DB_PATH` sí requieren reinicio.

Destinatarios de correo: `PANELA_EMAIL_TO` recibe solo consultas externas (`ask_eta`); los reportes internos (`report`, incluyen notas del operador) van a `PANELA_EMAIL_REPORT_TO`. Sin esa variable el reporte por correo queda pendiente y nunca se desvía al destinatario externo. Ambos deben estar en `PANELA_ALLOWED_EMAIL_RECIPIENTS`.

Reintentos: un rechazo definitivo (HTTP 4xx, incluido 429, o Slack `ok:false`) queda `failed`, guarda el código del proveedor en `provider_error` (`invalid_auth`, `not_in_channel`, `validation_error`…) y puede reenviarse con **Reintentar envío**: no hubo entrega, así que no duplica. Timeout, HTTP 5xx o reinicio durante envío dejan `result_unknown`: en Slack no se reintenta a ciegas; en correo se permite reintentar dentro de 23 h desde el primer intento, porque Resend deduplica la misma `Idempotency-Key` durante 24 h. Las operaciones obsoletas se cancelan antes de enviarse.

Despachador automático (con `PANELA_LIVE_SEND=true` y `PANELA_AUTO_SEND=true`): el servidor revisa la cola al arrancar y cada 10 s. Envía todo mensaje pendiente de la versión vigente del caso (también los creados con el envío apagado o el servidor caído) y reintenta los `failed` con espera creciente de 1, 2, 4 y 8 min, hasta 5 intentos automáticos. Al cambiar `.env` se reactivan los reintentos de todos los fallidos. `result_unknown` nunca se reintenta automáticamente; en correo queda disponible **Reintentar envío** dentro de la ventana de idempotencia.

Con `OPENAI_API_KEY` y `OPENAI_MODEL` explícitos, Responses propone una intención mediante función con esquema estricto; una política determinista limita el intento según estado. No observa imágenes, decide stock, cambia permisos, genera destinatarios ni realiza envíos. Si falla, la decisión registra fallback a reglas. No se ha probado la integración autenticada. Es una propuesta acotada adicional; el flujo básico es de reglas. Referencia: [Function calling](https://developers.openai.com/api/docs/guides/function-calling).
